# 提交规范：一个成果 = 一次提交

> 你定的规矩：**有具体成果产出就提交一次 GitHub。**
> 这条规矩的价值不在"备份代码"，而在 15 周后你能指着 commit 历史说：这个人每一天都有可运行的产出，而且每个决定都能追溯。面试时被问"你做过什么"，你有 200 条记录；被问"为什么改这里"，你能翻到当时的 commit。

## 一、什么算"成果"（判据）

满足**任意一条**就可以提交：

1. 有个东西**能跑**（脚本能执行、接口能访问、页面能打开）。
2. 有份东西**能看**（README、评测报告、成本表、架构图、复盘）。
3. 有个**结论能复用**（消融对比、badcase 归因、踩坑记录）。

不算成果，别单独提交：

- 只改了编辑器设置、格式化了一行、`.venv` 变了。
- "今天学了一下午但什么都没产出"——这种情况记进 [进度看板.md](../进度看板.md) 的卡点清单，不要用空提交假装有进度。

## 二、仓库怎么分（现在只建 1 个）

| 仓库 | 放什么 | 什么时候建 |
|---|---|---|
| `agent-learning-log` | 这个工作台：进度看板、笔记、docs、W01 打底代码 | **明天（D1 收尾）** |
| `rag-kb-agent` | 项目一：企业知识库 RAG Agent | W2 开始 |
| `longtask-agent` | 项目二：LangGraph 长任务 Agent | W6 开始 |
| `<你的垂直场景>-agent` | 项目三 | W11 开始 |

为什么最后是 4 个仓而不是 1 个：简历上一个链接点进去就是项目一的可运行说明，比"在一堆学习笔记里翻第 37 个目录"强 10 倍。但现在**只建第一个**，别一次开四个然后空着——空仓库是负面信号。

## 三、commit message 格式

```
<类型>(<周次/日期>): <做了什么，用动词开头>
```

| 类型 | 用在 | 例子 |
|---|---|---|
| `feat` | 新功能、新脚本、新接口 | `feat(w1d2): CLI 助手 v0，pydantic 配置 + logging` |
| `fix` | 修 bug | `fix(w1d2): .env 引号未剥离导致 key 带空格` |
| `docs` | README、笔记、报告、成本表 | `docs(w1d4): 20 次调用的成本表与忙闲时对比` |
| `test` | 测试用例 | `test(w2d5): 检索接口补 8 个 pytest 用例` |
| `exp` | **评测 / 消融 / 对比实验** | `exp(w4d3): 开 Rerank 后 Recall@5 64%→88%，答案准确率 +9pt` |
| `refactor` | 不改行为的重构 | `refactor(w3d1): 拆出 retrieval 模块` |
| `chore` | 环境、依赖、配置 | `chore(w1d1): 环境清单 + uv 工程初始化` |

**`exp` 这个类型是这份计划的杀手锏。** 大多数人的 commit 历史只有 feat/fix；你的历史里有一串带数字的实验记录——`exp(w4d3): Rerank 开启后 Recall@5 64%→88%`。面试官翻到这一条，会直接问"为什么"，而你有消融表、有评测集、有报告。这就是"能评测"的证据链。

**写 message 的硬要求**：说清"改了什么"，不写"update"、"修改"、"111"。三个月后你自己看不懂"update"。

## 五、tag 计划（简历和面试都用得上）

| tag | 时间 | 含义 |
|---|---|---|
| `w1-done` … `w15-done` | 每周日 | 周节点 |
| `gate-1` | 12.20 | 项目一上线（公网 URL） |
| `gate-2` | 01.17 | 项目二 12 步长任务可恢复 |
| `gate-3` | 02.14 | 项目三上线 + 50 条 benchmark |
| `gate-4` | 02.28 | 简历/作品集定版 |

面试被问"你项目现在什么状态"，答"最新是 gate-3 tag，比 gate-2 多了 50 条垂直 benchmark 和成本面板"——这比"做完了"有信息量得多。

## 六、每次提交前的 30 秒自查

```powershell
git status --short
git diff --cached --stat
```

四条红线，任何一条不满足就**别提交**：

1. **没有 `.env`、没有 `sk-` 开头的字符串**。密钥进过一次公开仓库，GitHub 会永久留档。`.gitignore` 已挡，但你自己 `git add -f` 或改文件名就能绕过——所以每次提交前扫一眼。
2. **没有大文件**（>5MB 的模型、数据集、PDF）。需要的话用 Git LFS 或放对象存储，链接写进 README。
3. **没有 `.venv`、`node_modules`、`__pycache__`**。已 ignore，别用 `git add .` 到失控。
4. **提交能单独看懂**。如果 message 里要写"顺便还改了……"，说明该拆成两次提交。

## 七、一个常见错误：把提交当备份

"反正推上去了就等于存了"——这是把 Git 当网盘。区别在于：

- 网盘备份的是**文件状态**；Git 记的是**你为什么改**。
- 所以每次提交都要能回答一句"这次提交让项目多拥有了什么能力"。答不出来，说明这是一次备份，不是一次提交。

判断方法：写完 message，念一遍。念得像"给三个月后的自己发的一条工作简报"，就对了。

## 八、明天开工顺序（大约 3 小时，把 D1 补掉 + D2 开个头）

1. **Git 补配置**（2 分钟）：`core.autocrlf input`、`init.defaultBranch main`。
2. **建仓库推上去**（10 分钟）：
   ```powershell
   cd C:\Users\吴晨希\Downloads\Agent开发学习
   git init
   git add .
   git status --short          # 自查：不该看到 .env
   git commit -m "chore(w1d1): 学习工作台初始化（进度看板 + 安装清单 + 工具脚本）"
   git branch -M main
   git remote add origin git@github.com:<你的用户名>/agent-learning-log.git
   git push -u origin main
   ```
   先在 GitHub 网页上建**空仓库**（不要勾 README、不要 .gitignore），否则 push 会被拒。
3. **WSL2 + Docker**（30—60 分钟，含重启）：按 [安装清单.md](安装清单.md) 第 2、3 步。
4. **DeepSeek Key + 首次调用**（20 分钟）：`uv sync` → `first_call.py` → 看到 `calls.jsonl`。
5. **提交 D1**：`chore(w1d1): 环境自检 + DeepSeek 首次调用与成本记账`。
6. 有剩力就开 D2 的 CLI 助手骨架，提交一次 `feat(w1d2): ...`。

**关于进度错位**：D1 挪到明天，等于整体晚一天。不用焦虑——用上面这个顺序，明天结束时你实际完成了 D1 全部 + D2 一半，周日前能回到正轨。真正该盯的不是"第几天"，是**每周日有没有 `w1-done` 这个 tag**。
