## 2. 今天踩的三个坑（都是"操作事故"，不是理解错误）

**坑 1：`__repr__` 覆盖了，key 还是泄露。**
- 现象：`print(settings)` 输出完整 key，尽管已经重写了 `__repr__`。
- 根因：`print()` 调的是 `__str__`，不是 `__repr__`。而 pydantic 的 `BaseModel` **自己实现了 `__str__`**，所以只覆盖 `__repr__` 没用。
- 修复：类体里加一行 `__str__ = __repr__`（4 空格缩进，和 `def` 对齐）。
- 教训：**安全相关的类，两个方法都得覆盖**。日志用的是 `__str__`，很多密钥泄露就死在这一步。

**坑 2：`__str__ = __repr__` 写进了方法体里。**
- 现象：`NameError: name '__repr__' is not defined`。
- 根因：缩进 8 格 → 成了方法内部的局部变量赋值；而且 `__repr__` 这个名字在局部/全局作用域里都不存在（它只是类属性）。
- 教训：**4 空格 = 类成员，8 空格 = 方法体**。Python 用缩进表达作用域，这是最需要形成肌肉记忆的一条。

**坑 3：新旧代码叠在一起。**
- 现象：同一个类里出现两个 `from_env`，旧的那个还把缩进搞坏了（`IndentationError`），另外 `if "=" in line` 条件写反了。
- 根因：粘贴新代码时没先删旧的占位块。
- 教训：**粘贴前先确认"这块的边界"**——从哪行到哪行，删干净再贴。真实工作里改代码远多于从零写，这个动作每天都会重复。

## 3. 今天学到的方法（比代码重要）

1. **先侦察数据，再写解析逻辑**：用 `repr()` 打印 `.env` 的每一行，亲眼看到"有一个空行""key 长什么样"，然后三个 `if ... continue` 才有依据。
2. **`print` 用 `__str__`，`repr()` 用 `__repr__`，容器用元素的 `__repr__`**。
3. **`setdefault` 表达优先级**：真实环境变量优先于文件，这是容器部署能覆盖镜像内配置的基础。
4. **自定义异常 = 让上层能分类型处理**：`ConfigError` 该退出，其它异常可能该重试。
5. **失败要早**：配置错在启动时就说，而不是跑到业务中途才崩。
6. **`from_exc` 保留异常链**：给人看人话，给自己留线索。
